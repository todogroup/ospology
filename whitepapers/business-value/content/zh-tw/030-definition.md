# 什麼是開放原始碼？

即使在軟體工程師之間，對開放原始碼仍有許多誤解。那麼，開放原始碼究竟是什麼？

## 法律定義

開放原始碼軟體源自 1970 年代興起的自由軟體運動。軟體是第一種「數位產品」。早在數位音樂或數位書籍出現之前，人們就能免費複製軟體程式，而且完全不影響原始程式。這催生了一套政治哲學：程式設計師不應對軟體收費，而軟體應成為賦予使用者自主能力的工具。自由軟體運動所說的「自由」（free）指的是自由，而不是價格為 0 美元。自由軟體運動有四項基本自由：

- 可基於任何目的，依自己的意願執行程式
- 可研究程式的運作方式，並加以修改，使其依自己的意願運作
- 可再次散布副本，藉此協助他人
- 可將修改後的版本副本散布給他人

開放原始碼軟體運動承襲自由軟體運動的理念並將其明文化，為自由軟體建立法律架構，讓企業更容易接受，尤其是企業內的法務部門。

負責將開放原始碼軟體理念轉化為具體法律條款的組織是 [Open Source Initiative](https://opensource.org)，又稱 OSI。軟體只有在依軟體授權條款發布後，其他人才能使用；而 OSI 負責判定哪些授權條款屬於開放原始碼授權條款。[這裡](https://opensource.org/licenses)可查看經 OSI 核准的授權條款清單。

簡單來說，開放原始碼軟體就是依 OSI 核准的授權條款發布的軟體。

它可以發布在任何地方；可以由志工建立與維護，也可以由大型科技公司的員工負責；可以用來行善，也可以用來作惡。它可以由一個人或一群人製作，可以是多家公司協作的成果，也可以完全由單一公司建立。開放原始碼軟體在倫理或道德上並不必然優於專有軟體；它是一種授權模式，同時可能帶來優點與缺點。

未依 OSI 核准的授權條款發布的軟體，就不是開放原始碼軟體。

上述這一點非常重要，因為生態系中有些參與者試圖模糊開放原始碼的定義，或將其描述成一段連續光譜。開放原始碼並非光譜；一套軟體不是具備 OSI 核准的授權條款，就是不具備。

[這裡](https://opensource.org/osd)可查看 OSI 用來判斷特定授權條款是否符合標準的完整說明；簡要而言，授權條款必須符合下列標準：

1. 可自由再次散布。
2. 原始碼必須可取得。
3. 可自由建立衍生作品。
4. 不得歧視任何個人或群體。
5. 不得歧視任何使用領域。

其中有些條款乍看十分直觀，實際上卻不然。例如，開放原始碼軟體不能限制只能用於程式作者認定的「良善」用途。敵對國家可以將開源軟體用於間諜軟體或網路戰爭技術組合，也可以用於武器技術。軟體作者的商業競爭對手同樣可以使用開放原始碼軟體。由於貢獻內容必須經專案維護者核准，因此可以限制誰能為軟體做出貢獻，卻不能限制誰能使用軟體並從中受益。

## 法律上的開放原始碼與文化上的開放原始碼

人們之所以經常混淆何者屬於或不屬於開放原始碼，是因為開放原始碼雖有法律定義，許多開源活動背後卻還連結著更廣泛的理念與文化。開放原始碼軟體開發也有一套常見實務，將在下文說明。必須注意的是，這些實務雖與開放原始碼密切相關，卻不能用來界定一套軟體是否屬於開放原始碼。例如，程式碼可在 GitHub 上公開取得，不代表它就是開放原始碼；許多非開放原始碼授權條款也會公開程式碼，但其授權條款不符合 OSI 的開放原始碼標準。反過來說，也不是所有開源軟體都能在 GitHub 上取得。軟體可能放在 GitLab，也可能直接從網站下載；如果想回到過去，甚至可能放在軟碟片上。
接下來進一步探討開源文化的幾項支柱。

### 協作

多數開放原始碼軟體會發布於 GitHub 或 GitLab 的公開儲存庫中。這不僅能公開程式碼，也有助於協作。

並非所有發布於 GitHub 的軟體都採用開放原始碼授權條款；相反地，一套軟體若能直接從作者網站下載，且採用開源授權條款，它就是開放原始碼軟體，即使沒有方便的協作方式也一樣。

開放原始碼軟體之所以與 GitHub、GitLab 等協作平台緊密相連，是因為協作正是開源文化的核心。

並非所有開放原始碼專案都如此，但許多專案確實是協作成果。參與專案的人可能包括志工，以及受雇投入開源工作的成員；他們可能任職於彼此競爭的公司，也可能分散在世界各地，具備不同技能，經濟條件更可能有極大差異。專案可以由一位或多位維護者負責掌舵整體方向；即使每個人的參與程度差異極大，專案仍可以是社群共同投入的成果。

軟體開發者想到開放原始碼軟體時，往往會想到 Linux 之類的專案：正如上述情況，由來自各地的大批參與者共同建立；儘管現實條件差異甚大，他們仍找到一起合作的方法。

協作既可能是開放原始碼的優勢，也可能是弱點。運作順利時，軟體能獲得具有各種使用情境的人提供意見，每個人也能依自身專長做出貢獻。如此一來，軟體的開發速度能大幅加快，錯誤也能更快被發現與修正。

另一方面，協作並不總是容易，也有其缺點。開放原始碼專案可能被拉往無數不同方向；品質不佳的程式碼提交、內容不合理或重複而浪費時間的留言與議題，以及對同一問題解法的不同意見，也可能使專案陷入停滯。

協作被視為開放原始碼「精神」的一部分。然而，認為所有開源專案都是互不相識的開發者協作而成，基本上是一種迷思。許多開源專案由單一個人建立、開發與維護；也有許多專案由同一組織的多名成員建立並維護，其「協作」程度與任何內部開發的軟體並無不同。

### 透明度

開源文化的第二項支柱是透明度。在「理想的」開放原始碼世界中，這代表與專案相關的一切都公開進行：公開提出議題、公開討論發展藍圖，並以公開方式逐步開發程式碼。技術決策也能夠而且應該透明地進行。

由於程式碼必須公開取得，開放原始碼軟體顯然至少需要具備最低限度的透明度。不過，即使不公開開發流程，仍完全可以依 OSI 核准的授權條款發布開源專案。在開放原始碼領域，這稱為程式碼傾印（code dump）：程式碼完全在內部撰寫，等成品完成後才依開放原始碼授權條款發布。「程式碼傾印」帶有貶義，並被視為完全不符合開源精神。

透明度可能令人感到不自在，對公司而言尤其如此。許多公司不願發布開放原始碼軟體，正是擔心家醜外揚，或讓全世界看見不夠完善的工程實務。真正的透明度也與協作相伴；公開決策方式時，也代表願意聽取使用者的意見。
如果決策的過程與原因有公開紀錄，其他人也更容易理解並信任其結果。

### 社群

開放原始碼專案不只期待成員彼此協作，也期待他們建立連結，形成社群。

談到開放原始碼時，總免不了提及社群。那麼，社群究竟代表什麼？

協作是開源理念的核心價值之一，社群也是如此。對開放原始碼的理想主義者而言，目標不只是打造能解決實際問題的優秀軟體，還要凝聚理念相近的人，一同合作並彼此交流。開放原始碼在最佳狀態下關注的不只是軟體，也關注打造軟體的人。

社群可以有許多不同形式。在開源專案中，最基本的形式是 GitHub 上的討論與議題。開發者可藉此討論在軟體中發現的錯誤、專案應新增的功能，以及解決技術問題的不同方法。

許多開放原始碼專案也設有 Slack 或 Discord 群組，讓專案使用者彼此聯繫、提問並互相協助。這些群組有時就被稱為「社群」。

開放原始碼專案中最成功的社群營造案例，往往來自專案維護者能讓參與者在現實生活中相聚，一同合作並互相學習。這類活動有時是小型在地聚會，有時則是大型研討會，例如 KubeCon 或 Apache Foundation 舉辦的 Community over Code。

不過，正如協作與社群的其他面向，發布開放原始碼軟體並不要求一定要建立社群。社群也不會憑空出現；如果沒有積極投入社群營造，所建立的專案周圍通常不太可能自然形成社群，儘管並非完全不可能。

事實上，並非所有專案都適合建立社群。因此，社群營造雖是開放原始碼的核心價值，並非所有開源專案都會擁有社群，也不是每個專案都能從社群中受益。

## 專案內的不同參與程度

如同任何社群，開放原始碼專案的社群成員也有各種不同的參與程度。

### 使用者

在任何開源社群中，絕大多數人只是匿名使用者。開放原始碼專案的維護者面臨的一項挑戰，就是幾乎沒有這些人的資訊，因此往往很難了解實際情況。下載次數是一項可能的資料指標，但能提供的資訊仍然有限，因為這個數字無法顯示人們是否真的使用該軟體，也無法得知他們再次散布軟體，或隨產品一併提供軟體的頻率。

專案建立者與維護者幾乎無從了解 95% 的開源專案使用者，這常令人感到挫折。雖然仍可取得一些衡量指標，但多數時候必須接受一項事實：對社群這個部分的掌握程度非常有限。

由於許多開放原始碼軟體整合於其他軟體之中，後者的使用者通常不知道，或不在意自己嚴格來說也是其中所整合開源軟體的使用者。

### 提問與回報錯誤的人

匿名使用者中，最終會以任何形式與社群交流的人通常不到 5%。不過，即使只是登入 Slack 或 Discord 群組提問，也算是參與社群；這不僅為使用者體驗或說明文件的潛在問題提供線索，也讓對方表明身分，並提供如何使用軟體的相關資訊。

討論開源社群時，人們往往忽略這些活躍的社群成員，因為焦點經常集中在貢獻者，尤其是程式碼貢獻者身上。這也說明了為何沒有簡短詞彙可以稱呼「活躍於社群、但並非貢獻者的專案使用者」。

### 回答問題的人

健全的開源社群中，有一類社群成員價值極高，卻經常遭到忽略：無償為他人提供支援的人。換句話說，就是積極參與討論並回答他人問題的人。

這些人不一定會以貢獻程式碼或說明文件的方式為專案做出貢獻，但他們為專案與社群提供了極其重要的服務。沒有簡短詞彙可以稱呼這些人，但真正圍繞專案建立社群的正是他們，其影響甚至超過貢獻程式碼或說明文件的人。

### 貢獻者

貢獻者是對專案開發做出具體貢獻的人。在開源生態系中，人們談論的往往主要是程式碼貢獻者，但個人可用許多方式為開放原始碼專案做出貢獻，例如撰寫說明文件或網站內容、翻譯說明文件或使用者體驗內容、在研討會上介紹專案等。

### 維護者

維護者是掌握專案關鍵權限的人。他們決定專案的發展方向、接受或拒絕哪些貢獻，以及優先實作哪些功能。從較技術性的角度來說，維護者擁有程式碼庫的寫入權限，並負責發布版本。

專案建立之初，維護者就是專案建立者；但為確保專案延續，招募其他維護者十分重要。大型專案通常有多位維護者，而擁有一位以上的維護者，往往被視為專案健全度的重要指標。
