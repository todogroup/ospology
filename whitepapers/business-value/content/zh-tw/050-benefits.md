# 開放原始碼軟體的商業效益

## 創新

即使只是使用開放原始碼專案，也能運用眾多使用情境、個人及產業所累積的經驗。參與開放原始碼專案，甚至發布自己的專案之後，便能更快看見一套軟體如何應用於各種新穎情境，也能迅速取得不同使用情境及邊界案例的回饋。

開放原始碼專案的回饋週期遠比封閉原始碼專案短。如果開發一套主要供內部使用的軟體（也就是組織並非軟體供應商），所能取得的回饋僅來自公司內部使用者。因此，很可能會忽略軟體的許多潛在用途，也看不到它在其他產業中的應用情境。

## 提升工程品質

提升技能是深入參與開放原始碼時經常被提及的優點之一；開源社群也常指出，許多人共同檢視程式碼，有助於找出潛在錯誤，包括安全性漏洞及其他問題。無論如何，知道自己的成果將公開供全世界查看，也會產生心理作用，促使工程師撰寫更整潔的程式碼。經過多年實踐並擴及整個工程團隊後，即使未接受特定訓練，也能顯著提升工程品質。

然而，工程品質的提升不只源自程式碼受到公開檢視。參與開源社群也能讓工程師接觸更廣泛的經驗及更多元的導師。能提供回饋的人數增加後，工程師的技能水準也會隨之提升。

## 提升工程開發速度

毫無疑問，開放原始碼整體而言能提升工程開發速度；即使只是使用開放原始碼軟體，未以其他方式參與社群，也同樣能夠受益。

對於成為貢獻者，或發布及維護自有專案的工程團隊而言，開發速度上的優勢也可能相當顯著；不過，組織深入參與開放原始碼後能進一步提升速度，這一點不見得顯而易見。

先從將錯誤修正及新功能回饋給組織經常使用的專案談起。首先，組織將錯誤修正回饋社群後，其他社群成員便能處理其他議題，例如修正其他錯誤或開發新功能。如果組織本來就使用該專案，把無論如何都必須完成的工作回饋社群，就能讓專案以更快的速度向前推進；當所有仰賴該專案的組織都這麼做，專案進展就會大幅加快。

此外，貢獻專案的過程也會加深團隊對專案運作方式的了解。GitLab 設有鼓勵付費客戶向開放原始碼專案貢獻程式碼的計畫；他們發現，客戶參與貢獻後，會比原本更充分運用 GitLab。參與專案並回饋錯誤修正，在其他專案中也會產生類似效果。

另一種情況是將內部軟體專案發布為開放原始碼專案。有時這麼做不會帶來太多成果，因為專案只是放在 GitHub 上，未能吸引任何人的關注。不過，如果能以發布為開放原始碼的內部軟體專案為核心建立社群，通常就能招募其他人協助開發；也可能找到能達到相同成果的既有專案，進而與其維護者攜手合作。

## 與他人建立關係

開放原始碼與封閉原始碼軟體的眾多差異之一，在於開源從根本上不只是建立軟體產品，更是在個人及組織之間建立關係。

對個人的好處相當明顯：在日常工作中貢獻開放原始碼專案，及／或發布與維護專案時所建立的關係，有助於提升自身技能、拓展人脈，並在未來帶來更多職涯機會。對其所屬組織而言，與相近領域及截然不同領域的人合作，不僅能為正在進行的軟體專案帶來效益，也可能創造專案以外的價值。

對於彼此並非競爭對手、但所處產業相關的組織而言，透過開放原始碼專案建立的關係，可能促成其他聯合專案。這些機會可能演變為聯合行銷、產品組合銷售，以及遠超出最初促成兩家公司合作之軟體專案的其他商業機會。

面對不知如何處理的挑戰時，這些關係也讓團隊成員有其他對象可以求助，無論挑戰是否與促成彼此相識的開放原始碼專案直接相關。

參與既有的開放原始碼專案，必然會在團隊成員及其他公司同儕之間建立對等關係；自行撰寫、發布及維護開放原始碼專案，則讓組織有機會成為共同興趣社群的中心，匯聚一群同儕。兩個或更多組織也可以共同撰寫、發布及維護一項開放原始碼專案。較常見的情況是由一個組織撰寫初始專案，再招募其他組織的維護者加入；不過，兩種情境都能在個人與組織之間建立關係，進而帶來更多商業及技術機會。

## 招募

組織是否難以招募工程師？新進工程師到職的流程，是否漫長又造成所有人的負擔？如果答案是肯定的，更深入參與開放原始碼就是招募工程師的最佳方式之一；相較於任何程式設計測驗，這也能更準確地評估工程師的技能水準，並大幅加快新人到職與適應流程。

無論是貢獻既有專案，或將內部軟體發布為開放原始碼專案，負責管理開源關係的團隊成員都會與社群中的其他人建立關係。如前所述，這可能帶來更多商業機會，也代表已有一群工程師熟悉、可供延攬的人才。當然，前提是組織在所參與的社群中備受尊重；如此一來，公司的職場吸引力也會勝過其他公司。根據 Linux Foundation 的《State of Open Source in 2025》，74% 的受訪專業人士認為，參與開放原始碼能提高公司對人才的吸引力。

此外，如果招募的工程師本來就參與團隊也在投入的開放原始碼專案，組織便能比程式設計測驗更準確地評估其技能水準。可以查看此人的 pull request 及提出的議題；同樣重要的是，也能觀察此人如何與社群中的其他人互動，以及是否具備良好的協作能力。換言之，組織能大幅降低招募決策的風險。對潛在受聘者而言也是如此：相較於其他任何情況，他們能掌握更多關於組織及其工作方式的資訊，因此也能降低接受這份工作的決策風險。

在新人到職與適應方面，從雙方原已共同參與的開放原始碼專案中認識的人才，具有一項重大優勢：此人對組織參與的至少一項專案已經完全熟悉，從到職第一天起就能繼續貢獻。同樣重要的是，團隊很可能在此人到職前就已充分了解其優缺點，因此能據以調整新人適應流程。

## 留任

一般而言，工程師希望能貢獻開放原始碼專案，也可能希望建立自己的開放原始碼專案。如果能將這些活動納入工作，他們就更可能留任。Linux Foundation 的《State of Global Open Source 2025》報告指出，78% 的受訪者認為，參與開放原始碼能讓組織成為更好的工作場所。因此，雖然參與開源很可能提升團隊成員的整體技能水準，並為他們帶來更多職涯機會，卻也會提高他們對組織的忠誠度，因為他們知道並非所有組織都允許員工持續參與開放原始碼。

## 能見度

參與開放原始碼是額外的「行銷」管道，能提升組織的能見度。如前所述，這對招募開發者尤其重要。不過，招募並不是組織希望提高能見度的唯一理由；參與開放原始碼專案同樣有助於達成其他目的。

對於開發及銷售軟體的公司，提高能見度的優勢最為明顯。這類公司的目標客戶很可能參與開放原始碼專案，也知道有哪些組織投入其中，因此參與開源能直接帶來新客戶。即使是軟體工程師未必屬於目標市場的非軟體公司，在開源領域保持能見度也能提高組織整體的知名度。

此外，並非所有開放原始碼專案都主要由軟體工程師使用。有些開放原始碼專案確實屬於深度科技，只有程式設計人員使用；但另有許多專案聚焦特定產業，其終端使用者不具技術背景。參與深度科技專案能提高組織在程式設計人員之間的能見度；參與特定產業的開放原始碼專案，則能提升組織在所屬產業中的知名度，觸及潛在客戶及合作夥伴。

## 聲譽

參與開源社群，即使只有工程團隊參與，也能建立組織的聲譽及品牌。貢獻及／或維護開放原始碼專案的組織可以展現工程品質，不僅有助於招募；對於銷售各類軟體的公司，也能建立客戶信任。

參與開放原始碼所帶來的聲譽效益，不只是展現內部工程能力；如果組織不只貢獻程式碼，也加入專案維護團隊，並公開成為專案的支援者，效益更為顯著。假設組織投入一項安全性相關專案，不但聘用工程師參與專案，也為專案提供資金及／或其他支援。參與這項專案能提升組織的聲譽，使外界認為公司重視安全性，並具備確保自身軟體安全的內部專業能力。如果客戶及協作者重視安全性，這種聲譽提升就能直接協助公司取得交易並促成合作關係。

當然，開放原始碼也伴隨聲譽風險：與其做得很差，還不如完全不做；面對開放原始碼專案這類高度公開的事務時尤其如此。如果程式碼草率，或團隊成員在所參與的開源社群中不當對待他人，組織的聲譽就會受損。這正是組織應訂定開放原始碼相關政策的原因之一；如果工程團隊把開源社群當成毫無規範的蠻荒地帶，可能會傷害組織聲譽。

## 信任

信任是組織聲譽的一環。貢獻開放原始碼專案，以及建立與維護開放原始碼專案，有助於組織在整個生態系中，與不同類型的利害關係人建立信任，包括潛在員工、現有員工、投資人、合作夥伴及客戶。當然，前提是組織必須妥善投入。

參與開放原始碼能以幾種不同方式建立信任。首先是透明度。程式碼庫中可供合作夥伴、員工及客戶查看的部分越多，他們就越能自行驗證軟體確實只執行宣稱的功能，沒有其他行為。組織並非要求人們無條件信任，而是讓他們可以自行查核；當人們逐漸確認組織未隱瞞任何事，信任也會隨時間累積。

第二種信任來自公司在所參與的開源生態系中如何行事。公司是否是對社群有正面貢獻的成員？是長期投入，還是未建立專案關係就突然出現並提出要求？組織成員是否尊重開源生態系中的其他人？如果組織在開源社群中表現良好，合作夥伴、員工及客戶也更可能相信組織在其他情境下會採取良好作為。

## 新機會

參與開源社群，無論是建立與維護專案，或成為既有專案的積極貢獻者及社群成員，都能創造額外的商業機會，甚至帶來新的營收來源。

這種發展最典型的案例是 [Backstage](https://backstage.io)。這項專案最初由 Spotify 開發，並於 2020 年捐贈給 CNCF。Spotify 的核心業務與開發者入口網站或開發者工具完全無關，但 Backstage 成功後，Spotify 開始探索如何將這項原本在內部開發、用以解決工程團隊快速成長痛點的開放原始碼專案商業化。[Spotify 現在提供企業支援、Backstage 入口網站，以及數款付費的 Backstage 外掛程式。](https://backstage.spotify.com/partners/spotify/bundle/spotify-plugins-bundle/)並非每項開放原始碼專案最終都會成為營收來源，但起初作為內部工具、之後轉為開源，最終再分拆為新部門或新公司的軟體專案，其實並不罕見。

歸根究柢，參與開放原始碼能帶來額外商機及營收來源，無論是直接將開放原始碼專案商業化，或受益於開源協作所促成的合作關係。

## 充分發揮開放原始碼商業效益的策略

參與開放原始碼雖有許多潛在效益，但不會因為在 GitHub 上發布專案，或向所仰賴的專案提交 pull request，就自動實現。更難察覺的問題是，組織確實已從參與開放原始碼獲益，卻沒有人真正了解效益是什麼，也不知道對公司價值多少。發生這種情況時，組織對開源的投入便會面臨風險，因為預算緊縮時，企業領導者很可能刪減相關資源。之後企業因而受損，卻沒有人真正明白原因。

因此，組織必須有意識地規劃如何參與開放原始碼，並清楚傳達組織如何與開源互動，以及預期從中獲得什麼。當工程及企業領導者都了解開放原始碼的重要性，並將開源策略目標轉化為具體政策，藉此引導個別員工與開源互動，組織才能充分發揮開放原始碼的價值。相關政策應涵蓋從匿名使用開放原始碼，到何時及如何貢獻、發布及／或維護自有開放原始碼專案。

### 盤點目前參與開放原始碼的情況

如果組織目前有開發軟體，幾乎可以確定已經以某種形式參與開放原始碼。因此，要充分發揮開源帶來的商業效益，第一步就是釐清目前的參與方式。開放原始碼使用情況調查顯示，企業及工程領導者都大幅低估組織內部的開源使用程度；原因往往是工程師視開源為工作不可或缺的一部分，因而習以為常，也不會特別向主管提起。

當然，盤點開放原始碼參與情況還有其他理由。首先，單是了解使用了哪些專案，就對安全性十分重要，也是軟體物料清單（SBOM）的重要部分。但就開放原始碼專案而言，還有停止維護的風險。盤點開源參與情況時，應嘗試評估下列事項：

- 軟體堆疊中整合了哪些專案？
- 團隊經常使用哪些專案？
- 每項專案的重要程度為何？如果專案停止運作，會對組織造成什麼影響？組織內部自行修正問題的可能性有多高？如果專案停止運作，客戶是否也會受到影響？
- 除了匿名使用專案之外，員工是否還參與任何專案？
- 如果員工參與了某些專案，具體參與方式為何？是什麼原因促使他們參與？
- 公司是否曾將任何專案發布為開放原始碼？由誰發布？是否仍有人維護？專案的權責歸屬為何？

### 評估目前從開放原始碼獲得的效益

開源倡議者與同事溝通時，最常感到挫折的原因之一，是難以清楚說明公司究竟能從開放原始碼獲得什麼；面對工程部門以外的同事時尤其如此。這是因為組織參與開放原始碼雖有一些常見效益，但每個組織都有不同情況。開源倡議者若要主張更深入參與開放原始碼專案，就必須先向企業利害關係人清楚說明組織目前從開源獲得的效益。

挑戰在於，開放原始碼帶來的效益通常是間接的，但並非一概如此。更大的風險是，公司若未察覺已經從開源獲得的效益，可能會因為認為沒有投資報酬而減少投入，之後才發現聲譽、能見度或招募能力下降，卻無法解釋原因。

完整盤點組織目前參與開放原始碼的情況後，就能開始評估這些參與為組織帶來了什麼。從開源獲得的效益未必立即可見；此時最佳作法是提出開放原始碼如何造福企業的假設，再加以驗證。

### 設定至多三項希望透過開放原始碼達成的策略目標

如上所述，參與開放原始碼可能出於許多不同的策略理由。然而，如果試圖從開源獲得所有效益，反而會分散心力，最終所得少於集中投入的情況。因此，組織最好為參與開放原始碼選擇至多三項策略目標，小型組織尤其如此。

大型組織很可能會針對不同的開放原始碼專案訂定不同策略目標。在這種情況下，每當團隊將內部軟體專案發布為開放原始碼，或開始以積極貢獻者身分深入參與既有專案時，都應明確訂定策略目標。任何特定專案都不應設定超過兩至三項策略目標。

無論討論的是公司整體參與開放原始碼的策略目標，或參與單一專案的策略目標，這些目標都不是一成不變。目標可以改變，而且應定期（每季或每半年）評估，以確認仍符合公司的整體優先事項，同時評估開源參與是否確實達成設定的目標。

### 參與具有策略重要性的專案

有一項顯而易見的事實仍值得說明：組織不會參與所使用的每一項開放原始碼專案，甚至不會參與所有重要專案。多數軟體堆疊包含大量開放原始碼軟體，組織不可能對每一項專案都作出有意義的貢獻，即使規模很小也一樣。不過，仍可找出對組織具有特殊策略重要性的開放原始碼專案並參與其中。參與開放原始碼專案有許多層次。如果修正某項專案中的錯誤，即使該專案並不具備特殊策略重要性，將修正回饋給專案對組織或個別軟體工程師都沒有壞處。這麼做能讓專案其他使用者及維護者處理其他事務，最終讓所有專案使用者受益，包括組織本身。既然無論如何都必須撰寫修正，就應將成果回饋社群。

除了單次錯誤修正之外，是否參與專案應出於明確意圖及策略考量。一般而言，組織應優先長期參與兩類專案：對組織具有特殊策略重要性的專案，以及對組織相當重要、但資源明顯不足或有停止維護風險的專案。

**具有策略重要性的專案**

成為開源社群信任的成員需要時間。如果個人或組織一加入開源社群，就立刻要求新功能或試圖影響發展藍圖，最好的情況是遭到忽略；最糟的情況則是列入拒絕往來名單，必須費力挽救受損的聲譽。

如果某項專案具有高度策略重要性，使組織未來可能需要影響其發展藍圖，或將新功能整合至專案，即使新功能由組織自行開發，最好也在真正有所需求之前就先參與社群。

能以策略層次參與多少專案，取決於組織規模。不過，如果希望有能力影響發展藍圖，或只是希望提交的 PR 能及時獲接受，就應在出現急迫需求之前，投入資源成為社群的一員。

**乏人維護的專案**

有些專案相當重要，甚至至關重要，卻不一定對組織具有策略重要性。不過，當一項對組織十分重要的專案有停止維護的風險，或維護狀況不佳時，組織參與其中可能是明智的作法。
