### 商業中的開放原始碼：Spotify 與 Backstage

> 注意：本使用案例以直接訪談該組織所蒐集的資訊為基礎，並在發布前由受訪者審閱。

成功的開放原始碼專案能確立公司在業界的領導地位、協助招募頂尖人才，並建立公司品牌。在某些情況下，它甚至能成為新的營收來源。Spotify 的 Backstage 正是這類案例。

早在建立 Backstage 之前，Spotify 就曾在內部建立尖端技術，但隨著新的外部技術成為業界標準，最終又以外部技術取代自有技術。例如，Spotify 在 Docker 出現前曾擁有自己的容器技術，但隨著 Docker 廣泛普及，最後便放棄該技術。

Backstage 初次開發時，團隊希望避免日後還得移轉至另一套解決方案；他們想讓全世界改用 Backstage，而非由自己再次移轉。若要讓這種可能性成立，唯一方法就是將 Backstage 發布成開放原始碼專案。

一開始，要讓 Backstage 成為業界標準看似遙不可及；更具體的目標，是攤提開發投資並取得外部貢獻，包括創新構想、意見，以及有助於維護專案的實際開發成果。Spotify 時任工程經理 Helen Greul 表示：「我們當時想，如果夠幸運，它會成為下一項廣泛普及的技術。事情也算是這樣發展了，我們開創了一個新的產品利基。」

#### 為發布作準備

Backstage 開源工作的主要推動者，是平台部門副總裁 Tyson Singer。不過，從董事會、產品經理到個別開發者，這項專案在公司內部都獲得廣泛認同。最初的主要目標是吸引貢獻，但當時已有七年歷史的原始 Backstage 帶有大量 Spotify 特有語意，且以 Java 撰寫。為提高吸引貢獻的機會，團隊決定以 TypeScript 重寫整個專案。

即使發布之後，團隊仍持續努力吸引貢獻。首先，Spotify 會在公司部落格及社群媒體上推廣 Backstage。Spotify 本來就擁有強大的工程品牌，許多人也真心期待一窺其內部運作方式。團隊也努力遵循良好實務，例如標示適合新手處理的議題、與社群展開對話，以及迅速合併 Pull Request——有時一天會合併多達一百個 Pull Request。

#### 商業利害關係人的角色

一開始，Spotify 的商業利害關係人對 Backstage 並沒有太大興趣；他們多半認為這麼做不會有害，而他們眼中建立專案的主要優勢，是塑造 Spotify 身為理想雇主的品牌形象，並確立其在尖端工程實務上的業界領導地位。Greul 表示：「他們沒有太多期待。我想結果讓他們頗為驚喜。」

起初，高階主管利害關係人並未反對，很大一部分原因是他們不太了解開放原始碼。Backstage 團隊必須向高階主管團隊說明軟體工程、開放原始碼概念，以及開放原始碼商業化。

隨著專案逐漸在廣大社群中形成聲勢，在公司內部也得到更多關注。第一年內，團隊就開始評估商機規模，並把 Backstage 視為真正的內部新創公司。例如，他們開始討論將專案捐贈給 Cloud Native Computing Foundation（CNCF）。商機逐漸明朗，而且 Backstage 正在解決一項他人尚未解決的痛點。Backstage 身為開放原始碼專案的成功，正好遇上高階主管開始推動 Spotify 營收來源多元化，減少對核心音樂串流業務仰賴的時期。因此，高階主管團隊同意進行獲利實驗；隨著獲利計畫日益成熟，團隊開始直接向最高管理階層報告，除了 GitHub Star 數等典型開放原始碼指標，也開始追蹤商業指標。

#### 建立關係

將 Backstage 發布為開放原始碼專案，也意外改變了 Spotify 與許多軟體供應商的關係。一方面，Spotify 仍是這些供應商的客戶；另一方面，Spotify 也會在 Backstage 上以外掛形式推廣供應商的軟體。這改變了雙方關係，讓 Spotify 在與軟體供應商談判時擁有截然不同的籌碼。

#### 給其他公司的經驗

建立開放原始碼專案時，應該要有明確理由。Greul 表示：「無論何時，公司內部都不應有人質疑這個專案為何存在。」這不代表理由必須一成不變；公司建立開放原始碼專案的目標，可以也應該隨著專案成熟，以及正面與負面的意外發展而改變。不過，公司全體始終都應對一套策略達成共識。

策略溝通同樣至關重要，卻經常遭到忽略；而且溝通同時包含內部與外部溝通。Greul 表示，最初參與 Backstage 的團隊只有約十人，當時應該投入更多心力徵求內部貢獻。
