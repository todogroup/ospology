本檔案除了說明開放原始碼領域的常用詞彙，也會簡要說明這些詞彙與商業領域的關係。某些詞彙經常以縮寫而非全名出現，遇到這種情況時也會一併列出縮寫。

# 前言

開放原始碼可分為工程驅動與商業驅動兩個面向。工程驅動面向在開放原始碼社群中通常已有充分呈現，商業驅動面向卻仍缺乏實用資料。
因此，我們共同編寫《Open Source in Business Guide》，希望說服商業人士將開放原始碼視為策略工具箱中的另一項策略工具。我們也希望提供良好實務與可重複運用的資料，協助組織內部的開放原始碼倡議者，說服企業主管考慮以開放原始碼取代傳統作法。

風險觀點固然重要，卻不是本商業指南的主要目標（這方面更適合由 OpenChain 社群或 TODO Group 的其他 OSPO 指南處理）。
儘管如此，仍應以冷靜且直觀的方式列出風險，說明這些風險可以管理，而且已有 ISO 標準可用於「安全又無聊地」處理風險（OpenChain 於 2023 年的年度格言）。
另一方面，這類處理方式並非毫無成本，而是必須對必要流程投入一定資源。

# 詞彙

- **開放原始碼（Open Source，OS）：** 依 Open Source Initiative（OSI）核准之授權條款發布的軟體。
- **開放原始碼計畫辦公室（Open Source Program Office，OSPO）：** 組織內部的專責團隊，負責制定政策與策略，以治理組織和開放原始碼之間的關係。
- **Pull Request（PR）：** 在程式碼協作平台（通常是 GitHub 或 GitLab）中，請求變更檔案或將檔案加入儲存庫。提交 Pull Request 可要求專案維護者進行審查，再由維護者決定拒絕或接受變更。
- **開放原始碼專案（Open Source Project）：** 開放原始碼軟體經常稱為「專案」。
- **儲存庫（Repository）：** GitHub 或 GitLab 等程式碼協作平台上的「檔案」，其中包含與特定專案相關的所有檔案。
- **使用者（User）：** 使用開放原始碼軟體的人！絕大多數開放原始碼軟體使用者完全匿名；開放原始碼軟體的一項挑戰，就是軟體維護者所掌握的使用者資訊非常有限。
- **貢獻者（Contributor）：** 對開放原始碼專案作出具體貢獻的人。在大多數情況下，這是指程式碼貢獻者，也就是為專案貢獻程式碼的人。不過，開放原始碼專案有許多不同類型的貢獻，包括撰寫文件、翻譯文件，或回覆社群中的問題。
- **維護者（Maintainer）：** 掌控開放原始碼專案發展方向的人。他們擁有程式碼庫的寫入權限，可以接受（或拒絕）Pull Request，並決定功能的優先順序。專案維護者對專案中的各項事務擁有最終決定權！
- **授權條款（License）：** 規範軟體產品使用方式的法律條件。軟體授權條款有許多種類，會規定軟體可如何使用及由誰使用。開放原始碼授權條款不代表可完全自由地任意處置程式碼；若要符合授權條款，仍必須滿足特定條件。

- **自由軟體（Free software）：** 一般而言，自由軟體比開放原始碼軟體提供更多自由。使用者應可享有絕對自由，依自身需求處置軟體。自由軟體被視為開放原始碼背後的理念，而開放原始碼則嘗試將自由軟體背後的理念付諸實行。
- **著佐權授權條款（Copyleft license）：** 一種賦予使用者相對較少權利的開放原始碼授權條款。寬鬆式授權條款與著佐權授權條款最顯著的差異，在於使用者採用著佐權授權條款時，必須以相同授權條款發布所有衍生作品，且不能以原始碼開發付費產品。當開放原始碼專案背後的公司試圖藉專案獲利時，這可以避免競爭者取用其原始碼並建立直接競爭的產品；但對於需要將開放原始碼納入自家軟體產品的企業而言，也可能造成問題。
- **寬鬆式授權條款（Permissive license）：** 一種廣泛賦予使用者權利的開放原始碼授權條款；使用者可以使用、變更及散布程式碼，甚至以其建立競爭軟體產品。最常見的寬鬆式開放原始碼授權條款是 MIT 與 BSD 授權條款。
- **貢獻者協議（Contributor agreement）：** 貢獻者（尤其是程式碼貢獻者）在貢獻獲得接受前簽署的法律協議。貢獻者協議通常涵蓋著作權讓與及授權等事項；如果專案日後變更授權條款，這份協議可能變得極為重要。若計畫藉由專案獲利，貢獻者協議也至關重要。良好實務是在接受任何人的貢獻前，先制定貢獻者協議。
- **文件（Documentation）：** 軟體的「使用手冊」。文件包含文字、圖解甚至影片，協助使用者成功安裝及使用開放原始碼軟體。並非所有專案都有文件！但開放原始碼專案隨附文件是一項良好實務。
- **發展藍圖（Roadmap）：** 專案的未來規劃。它可以只是一份日後要加入的新功能清單，也可以是複雜的策略文件，概述專案的未來願景、目標使用者社群、價值主張等內容。無論採用何種形式，發展藍圖都應引導專案未來的發展方向。
- **議題（Issue）：** GitHub 上的議題可用於留言、回報錯誤、提出建議，以及與開放原始碼專案的其他 GitHub 使用者進行各種討論。
- **社群（Community）：** 使用及參與開放原始碼專案的人。在開放原始碼領域，「社群」一詞經常出現，用法卻往往不夠明確。在理想化的開放原始碼軟體想像中，每個開放原始碼專案都有一群積極投入的志工，以及許多切身關注專案能否成功的人；但實際上，並非每個開放原始碼專案都有積極投入的社群。
- **社群版（Community edition）：** 在開放核心公司中，「社群版」通常是指開放原始碼專案。
- **開放核心（Open core）：** 一種開放原始碼專案獲利模式，其中有一項以該開放原始碼專案為基礎、依商業授權條款發布的付費軟體產品。軟體的「核心」是開放原始碼，但另有其他非開放原始碼功能。

# 概念

- Pull Request——這是一種請他人（通常是審查者）查看所提變更，並予以核准（合併）或拒絕的方式。
- 指導委員會（Steering Committee）——由一群人組成，負責監督開放原始碼社群或專案的活動。許多社群也稱其為理事會（Board），但 TODO 將其稱為指導委員會。
- 徵求提案（Call for Proposal）——會議、聚會及各類計畫藉此公開徵求提案，邀請人們在活動中演講或發表主題。
