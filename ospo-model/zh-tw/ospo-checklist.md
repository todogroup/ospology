# 📝 OSPO 檢查清單（台灣正體中文）

本清單是依「五階段 OSPO 成熟度模型」整理出的實務指引，聚焦已開始建立正式 OSPO 能力的階段 1 至階段 4。階段 0 是尚未建立正式流程的零星採用狀態，因此不另列檢查項目。本清單可協助從剛起步到已運作多年的 OSPO，檢視各階段的重點任務。
對應的研究請參考 **The Evolution of the Open Source Program Office（OSPO）**：
https://www.linuxfoundation.org/research/the-evolution-of-the-open-source-program-office-ospo

## 階段 1

- [ ] 定義計畫與品牌（例如 OSPO、開源倡議、開源營運負責人等適合組織語境的名稱）。
- [ ] 管理法律風險與授權：建立流程與文件，確保員工依照授權條款使用開放原始碼軟體，並避免組織因採用開放原始碼而承擔不必要的法律風險。
- [ ] 建立教育方案，協助開發者判斷何時適合使用開放原始碼軟體來打造新產品或服務。
- [ ] 建立軟體清冊流程，逐步整理出全組織層級的軟體物料清單（SBOM）。
- [ ] 讓組織了解開放原始碼的價值，以及合規、教育與 SBOM 等基礎能力的重要性。

## 階段 2

- [ ] 列出與開源專案互動的最佳實務，例如如何請求加入新功能、回報錯誤與提交程式碼貢獻。
- [ ] 向員工與管理階層說明「不只是使用開放原始碼，也要主動貢獻」的重要性；實務作法可以包含：倡議並推動活動贊助、協助專案維護者在公開技術論壇分享，或確保組織有資源投入關鍵開源專案。
- [ ] 透過激勵與支援機制，讓開發者參與對組織營運至關重要的開源專案，成為高度活躍的貢獻者，甚至是主要維護者。

## 階段 3

- [ ] 發起開源專案並負責其營運，或成為主要贊助者。
- [ ] 透過建立與啟動開源專案，在社群中累積廣泛信任與聲譽。
- [ ] 為專案投入一名或多名全職同仁（FTE），並承擔培育社群與維持專案健康發展的責任。
- [ ] 建立內部流程、操作手冊、檢查清單、工具與其他機制，用來審視、組織與營運開源專案，並持續培養與指導專案領導者。

## 階段 4

- [ ] 成為技術決策中的策略合作夥伴，協助制定開放原始碼選擇方針與長期承諾。
- [ ] 就「哪些開源技術應納入或移出組織技術堆疊」向 CTO 與技術領導團隊提供建議。
- [ ] 主導制定適合組織情境的開源專案評估基準（例如授權、治理、健康度等）。
- [ ] 協助組織理解並處理專案中的「社群政治」與治理議題，在多方拉鋸時保持專業與中立，並善用基金會或協作組織提供的中介角色。
